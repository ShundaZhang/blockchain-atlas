01 / FIELD NOTES

L2 moves work; the settlement path defines the guarantee

Ethereum rollups and Bitcoin payment channels are two different scaling models.

A rollup executes a separate state machine and publishes data and state commitments to Ethereum. L1 contracts enforce its specified proof and exit rules. The sequencer orders transactions; a batcher publishes data; independent nodes reconstruct the execution. These jobs can be operated by different components. A fast sequencer receipt is an early observation, not automatically final L1 settlement.

ModelWhat moves off L1What must be inspected
Ethereum rollupGeneral execution and application stateL1 data, proof system, bridge, upgrade powers
LightningUpdates between funded channel participantsLiquidity, latest state, deadlines and Bitcoin enforcement
Sidechain / validiumSeparate execution; possibly separate data availabilityOwn validators or external DA assumptions; not identical to a rollup

An L2 label is not a complete security description. Separate execution correctness, data availability, liveness and control. Lightning is already a deployed network; “recent developments” below concern its evolving protocols and applications, not a claim that payment channels were invented in 2026.

02 / FIELD NOTES

Optimistic and validity proofs enforce different acceptance rules

A state root is a commitment; it is not a proof that the transition is correct.

QuestionOptimistic rollupValidity-proof rollup
Proposed resultAn assertion that remains disputableA result accompanied by an execution-validity proof
EnforcementA challenger disputes an incorrect transition; an L1 game resolves itAn L1 verifier checks a proof for the specified program and public inputs
Exit timingDispute resolution and deployment-specific maturity delaysProof generation, submission, acceptance and bridge conditions
Additional assumptionsAvailable data and a timely honest challenger under the configured rulesSound proof system, correct circuits/VM, available data and valid bridge logic

In an interactive fault-proof design, execution traces can be narrowed down to a disputed instruction that L1 can check. A zkVM/zkEVM instead turns the chosen execution into constraints and generates a succinct proof. “Zero knowledge” in a rollup name does not mean transaction data or balances are private. A proof establishes the encoded statement, not every property of the application.

OP Stack’s fault-proof bridge separates proveWithdrawalTransaction from finalizeWithdrawalTransaction. Game outcome, proof maturity, additional delays and Guardian controls matter. Do not hard-code “all L2 withdrawals take seven days” or “ZK exits are instant.” A fast liquidity-provider exit adds its own pricing and counterparty mechanism.

03 / FIELD NOTES

Blobs and PeerDAS scale the data layer, not the EVM instruction rate

Data availability and execution validity answer different questions.

EIP-4844 introduced blob-carrying transactions: a blob contains 4096 field elements, occupying 131072 bytes, and has a separate blob-gas fee market. The EVM sees versioned hashes of blob commitments rather than arbitrary access to the blob bytes. Rollups post compressed data through this channel; normal execution gas is still a separate cost.

Blob availability is temporary, historically around 18 days under the original retention window. It is not permanent application storage. Rollup node operators and archival services must retain the history they need for reconstruction; a commitment alone cannot regenerate missing data.

PeerDAS, deployed with Fusaka, erasure-codes blob data into columns. Nodes custody assigned columns and sample availability instead of every node downloading every full blob. This allows blob capacity to rise with manageable per-node load. It does not verify rollup execution or make bandwidth free. Blob-parameter-only upgrades can adjust target/max counts; these are coordinated network changes, not automatic unlimited throughput.

04 / FIELD NOTES

Read an implementation by component and deployment

A shared framework does not imply identical data modes, governance or finality.

ExampleImplementation pathUseful question
OP StackRollup node + execution engine; batcher; assertions/fault games; L1 portalCan I derive the same L2 blocks from L1 inputs, and which game governs this portal?
Arbitrum NitroDeterministic execution and a proving representation; BoLD dispute machineryWhich execution and DA configuration does this chain use?
ZKsyncExecution, batch commitments, proving and L1 verificationWhich VM/prover version and settlement/DA mode apply here?

Developer workflow: choose the actual chain and test network → check chain ID and RPC → compile for its supported VM/EVM target → deploy and inspect receipts → test bridge messages and exits. EVM compatibility lets familiar Solidity tools carry over, but precompiles, fee accounting, transaction types and cross-domain calls can differ. A Hardhat execution on chain 31337 does not simulate a real rollup’s data publication or withdrawal contracts.

Study operational failures as part of implementation: stop the sequencer, observe the documented forced-inclusion path, reconstruct state from published inputs, and inspect upgrade/pausing authority. These are protocol-specific experiments, not consequences of choosing an L2 brand.

05 / FIELD NOTES

Lightning settles enforceable channel states on Bitcoin

Funding is on-chain; most balance updates remain between participants.

A payment channel commits Bitcoin funds to jointly controlled spending rules. Each side holds signed commitment transactions representing an enforceable state. Normal operation exchanges new commitments and revokes the previous state. In the established revocation-based design, delayed outputs and breach remedies discourage publishing a revoked commitment. The funding output remains the backing; participants do not mine a new Bitcoin block for every payment.

Teaching example: capacity = 100,000 sat
Initial: Alice 80,000 | Bob 20,000
Alice pays Bob 15,000
Updated: Alice 65,000 | Bob 35,000
Total capacity remains 100,000 sat

The example deliberately omits commitment fees, channel reserves, pending HTLCs and dust limits; usable spending capacity is therefore smaller than the simple total in a real channel. A cooperative close agrees on a settlement transaction. A unilateral close uses the enforced commitment/HTLC paths and can require waiting and additional on-chain fees. Lightning changes when settlement work is done; it does not remove the base chain.

06 / FIELD NOTES

HTLCs link several channels without a direct Alice–Carol channel

Value is forwarded toward the receiver; the preimage travels back.

Carol creates a random preimage r and publishes H=SHA256(r) in an invoice. Alice offers Bob an HTLC conditional on revealing r before an expiry; Bob offers Carol a corresponding HTLC with an earlier expiry. Carol reveals r to claim the payment; Bob uses it upstream. The timeout gap gives intermediaries time to enforce their claim if off-chain cooperation stops.

BOLT 4 onion payloads let each hop process its forwarding instructions; routing nodes do not receive the whole route in cleartext. They still observe their neighbors and local timing/amount information. This is routing privacy, not a universal anonymity guarantee.

A BOLT 11 invoice can carry the payment hash, amount, expiry and other routing/payment fields. Its payment_secret is not the secret preimage r. A valid invoice does not demonstrate that a usable route exists, and an invoice expiry is distinct from the individual HTLC on-chain deadlines.

07 / FIELD NOTES

Liquidity direction and operational state determine usability

Channel capacity is not the amount that can be sent in every direction.

A 100,000-sat channel with 80,000 on Alice’s side does not give Bob 100,000 sat of outbound liquidity. Receiving requires inbound liquidity from the peer side. On an Alice → Bob → Carol route, Bob’s channel to Carol can be the bottleneck even if Bob has ample balance elsewhere. Rebalancing, swaps, opening channels and liquidity services change allocation and can add fees or service dependencies.

A noncustodial operator must preserve current channel state and handle enforcement deadlines. Watchtowers can help detect revoked-state breaches while a client is offline, but do not route payments, guarantee all liveness, or replace backups. LND static channel backups support recovery through a closure path; restoring a seed is not the same as reconstructing every latest live channel state.

A custodial wallet can hide this complexity by operating channels for users, but then the user has a claim on its operator rather than independent control of those channel keys. Evaluate custody separately from the fact that a service uses Lightning.

08 / FIELD NOTES

Reproduce the payment lifecycle on a local regtest topology

Follow a real implementation without using public-network funds.

Polar uses Docker to run Bitcoin Core and Lightning implementations. Create three LND nodes, Alice, Bob and Carol, on a local regtest network. Fund Alice and Bob through Polar’s test-funding controls; open Alice–Bob and Bob–Carol channels and mine enough regtest confirmations. Ensure both forwarding directions have spendable liquidity. Open the node-specific terminals so that RPC/TLS credentials and ports refer to that node.

# Carol node terminal — configured local regtest only
lncli --network=regtest addinvoice --amt=10000 --memo="local routing lesson"

# Alice node terminal — paste the returned payment_request
lncli --network=regtest decodepayreq --pay_req="<REGTEST_INVOICE>"
lncli --network=regtest payinvoice "<REGTEST_INVOICE>"

# Inspect each node and the resulting channel balances
lncli --network=regtest listchannels
lncli --network=regtest listpayments

Check the decoded amount and expiry, payment status, route, fees and balances. Then disconnect Bob before a new payment, or create insufficient outbound capacity, and compare the failure. Finally cooperatively close a test channel, mine blocks and inspect settlement outputs. Record the installed node versions and negotiated features. These are instructions for a separate Polar environment; the website and its Hardhat ZIP do not launch or emulate LND.

09 / FIELD NOTES

Bridges add a cross-system verification boundary

Preserve asset identity, message origin and finality across the boundary.

A lock/mint bridge escrows an asset on the source chain and creates a representation on the destination; other designs burn/mint or exchange existing liquidity. The receiving contract must authenticate the source event, accepted state and message. A rollup’s canonical bridge, an issuer’s native deployment and a third-party wrapped asset are different objects even when a wallet shows the same ticker.

CheckWhy it matters
Chain + exact contract / asset IDA symbol or familiar address is not a cross-chain asset identity
Origin, nonce and replay protectionA valid message must not authorize a different domain or execute twice
Finality and verification mechanismReorganizations, proof rules, committees and multisigs create different failure modes
Upgrade powers and exit routeA paused/upgraded bridge can change practical control of the representation

Cross-domain calls are normally asynchronous. A completed source transaction does not by itself establish destination execution. Design retries, expiry, refunds and independent status tracking. Sharing an EVM or a rollup framework does not make separate chains one synchronous atomic execution environment.

10 / FIELD NOTES

Intents and smart wallets abstract the workflow, not the trust

Interoperability is becoming an application interface as well as a bridge mechanism.

An intent specifies an acceptable outcome rather than every execution step: for example, deliver at least 99 units of asset Y on chain B before a deadline in exchange for 100 units of X on chain A. A solver supplies a route or destination liquidity and later settles under the order’s rules. ERC-7683 defines shared cross-chain order/settlement interfaces; it does not itself verify all chains or guarantee solver competition, refunds or settlement safety.

ERC-4337 adds UserOperations, bundlers, an EntryPoint and optional paymasters. A paymaster can sponsor user gas, but somebody still pays and sponsorship has policies. EIP-7702, deployed in Pectra, lets an EOA delegate execution to selected code persistently. It is not a temporary one-call permission or an ERC-20 allowance; a failed execution does not automatically undo the processed delegation.

These mechanisms can hide network switching, repeated approvals and gas acquisition from users. Implementation still has to bind chain, recipient, asset, amount, deadline and authorization, and make delegation/recovery powers visible. “One-click” is a user-experience result, not a new consensus guarantee.

12 / FIELD NOTES

Lightning is evolving in channel control, invoicing and assets

Each new feature requires matching protocol and implementation support.

Splicing changes a channel’s funding transaction to add or remove capacity while retaining the channel relationship, rather than treating every capacity change as an unrelated close/open cycle. BOLT 2 now documents its negotiation; verify the peers’ versions and feature negotiation instead of assuming support on every wallet. BOLT 12 offers add an offer → invoice request → invoice exchange using onion messages and blinded paths. An offer is not simply a reusable BOLT 11 payment invoice.

Taproot Assets commits asset state in Bitcoin Taproot outputs and validates asset lineage with additional client-side proofs. Asset-aware edge nodes can quote asset/BTC conversions through RFQ and route over BTC liquidity, so intermediate BTC routers need not all implement every asset. Bitcoin’s base consensus still validates Bitcoin transactions, not an issuer’s fiat reserves or every asset-level rule. Participants retain asset-proof storage/verification duties.

The 2026 v0.8/SDK release is an implementation milestone for this model, not a declaration that all stablecoins, wallets or routes are available. Multi-asset payments retain issuer, redemption, pricing and edge liquidity dependencies. They expand the payment surface without turning Bitcoin into an Ethereum-style general EVM.

Compare ecosystem effects through a trust and operations matrix

Engineering interpretation: scaling changes costs, coordination and where power concentrates.

DimensionEthereum rollup ecosystemLightning ecosystem
Application surfaceMore affordable programmable applications; distinct chains divide liquidity and stateRepeated small payments and payment integrations; channel liquidity constrains reachability
Infrastructure rolesSequencers, provers, DA archives and bridge/message operatorsRouting nodes, liquidity services, watchtowers and asset edge nodes
ComposabilitySynchronous within one execution domain; cross-domain actions need explicit coordinationPayments compose across a route; this is not arbitrary shared contract storage
Control / exitInspect proof and DA mode, upgrades, censorship fallback and withdrawal conditionsInspect custody, latest state, liquidity, deadlines and unilateral-close conditions
MeasurementMeasure actual fee, batch/settlement lag and dependency failuresMeasure payment success, directional liquidity, routing fees and closure costs

For an application, draw who authorizes an action, who executes it, where its data lives, what makes it final and how the user exits during a failure. Compare these properties before ranking TPS. Faster networks can support new products while also concentrating control in sequencers, liquidity hubs or wallet providers. Decentralization must be evaluated across these roles, not inferred from a low fee or a protocol logo.
