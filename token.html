01 / FIELD NOTES

Create a fixed-supply ERC-20 learning token

A contract deployment creates token state, not a new blockchain.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.30;

import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

/// @notice Fixed-supply learning token. No public mint, owner, proxy or sale.
contract StudyToken is ERC20 {
    constructor(address recipient) ERC20("Study Token", "STUDY") {
        _mint(recipient, 1_000_000 * 10 ** uint256(decimals()));
    }
}

StudyToken inherits a pinned OpenZeppelin ERC20 implementation. Its constructor mints 1,000,000 STUDY to a chosen recipient, with 18 display decimals. Raw supply is 1,000,000 × 10¹⁸ units. No public mint, owner, proxy, transfer tax or sale mechanism is added; transfer and allowance behavior come from the library.

STUDY is an educational token name. Deploying it creates neither backing nor demand, a price, exchange listing or liquidity. Creating a token is different from creating a native coin with its own consensus network, and from operating a stablecoin issuer.

02 / FIELD NOTES

An approval grants a spender a bounded right

approve does not itself transfer tokens.

balanceOf records holdings; transfer moves the caller’s tokens; approve sets an allowance for a spender; transferFrom uses that authorization to move an owner’s tokens. The spender may be a contract or account. Allowance and balance are separate checks, so a large allowance does not create tokens.

Example: authorize 10 STUDY, then the spender transfers 4; remaining ordinary allowance is 6. If the owner has only 3, a request for 4 still fails. Infinite allowances and nonstandard tokens require additional interpretation. Revoke allowances that are no longer needed and identify the spender’s exact contract.

03 / FIELD NOTES

A token issuance workflow has several independent outputs

Specification, deployment and market operation are separate work.

StepOutput
SpecifyName, symbol, units, supply, allocation and every privileged power
Implement and testPinned source, successful compilation and positive/negative behavior checks
Deploy locally / testnetChain ID, address, constructor args, receipt and observed supply
Publish and verifySource, dependency versions, compiler settings and contract identity
Operate if neededSeparate distribution, liquidity and monitoring plans; deployment does not perform them

For a real public issuance, technical deployment is only one part of a broader financial and operational project. This tutorial stops at local/testnet engineering and does not create a sale, pool or public fundraising transaction.
