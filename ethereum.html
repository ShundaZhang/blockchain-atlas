01 / FIELD NOTES

Ethereum execution changes account and contract state

ETH is the native asset; a token is contract-managed state.

Ethereum accounts have addresses and state such as balances and nonces; contracts also have code and storage. A signed user transaction can transfer ETH, deploy code or call an existing contract. Token balances commonly live in a contract mapping rather than in a separate native coin ledger.

An EOA is traditionally key-controlled; a contract account follows code. Modern account-abstraction mechanisms add programmable account behavior, so the distinction is a starting model rather than the full design space. A wallet is software for constructing and authorizing actions.

02 / FIELD NOTES

EVM bytecode, state and gas form a deterministic computation

Validators must be able to reproduce the same transition.

Solidity source is compiled into bytecode plus an ABI. The EVM executes bytecode against an initial state and transaction context, meters work using gas, and either commits allowed changes or reverts the execution’s state changes. Determinism excludes direct arbitrary web requests and ordinary system randomness.

Storage persists across transactions; memory and calldata serve different execution roles. Events enter transaction logs for off-chain indexing. An event is not a replacement for contract state, and contracts do not query old logs as a general internal database.

03 / FIELD NOTES

Execution and consensus remain separate layers

The Merge changed Ethereum consensus to proof of stake.

Ethereum moved from proof of work to proof of stake in September 2022. Execution clients process EVM state and transactions; consensus clients coordinate proposals, attestations and finality. A complete node setup connects both responsibilities.

L2 scaling is another layer of design, not the same change as PoS. A rollup’s sequencer can order transactions while L1 contracts enforce a specified proof and settlement mechanism. Inspect what data and exit path are available during failures.
