01 / FIELD NOTES

Hashes commit to bytes, not to truth

Change the serialized input and the commitment changes.

A cryptographic hash maps arbitrary bytes to a fixed-length digest. Blocks can commit to their predecessor and transactions through hashes. Bitcoin uses double SHA-256 in important structures; Ethereum commonly uses Keccak-256. These are different algorithms: Keccak-256 is not interchangeable with standardized SHA3-256.

A correctly linked chain can be rewritten and relinked in a toy program. What makes a production history costly or unacceptable to replace is consensus, validation and finality assumptions. A hash of a false statement is still a valid hash.

02 / FIELD NOTES

A signature authorizes a precisely encoded message

An address identifies a destination or account; it is not a password.

Private keys produce signatures; public information lets validators check them. Signatures bind transaction fields, including relevant network/domain information. Changing recipient, amount or nonce changes the signed request. A signature can be cryptographically valid while authorizing an action the user did not intend.

Wallet seed phrases can derive many keys. Self-custody means the ability to authorize transactions and the responsibility to protect or recover those keys; it does not mean that contracts or stablecoin issuers have no other powers. Read typed data and transaction destinations before signing.

03 / FIELD NOTES

Merkle commitments support compact inclusion checks

A proof is meaningful relative to a trusted or verified root.

A Merkle tree combines child hashes into parent commitments. An inclusion proof supplies the sibling values needed to reconstruct a root from one leaf. The root must itself be connected to an accepted block or state; otherwise a producer can make a consistent tree of invented data.

Blockchains use different commitment structures and serialization rules. Inclusion does not prove that a transaction succeeded, that an off-chain statement is true, or that the block is final. A light client needs a method to validate the relevant header and consensus state.
