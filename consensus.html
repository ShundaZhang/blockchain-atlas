01 / FIELD NOTES

Validity, ordering and finality solve different problems

A producer proposes; validating nodes still check the rules.

Execution rules say whether a transaction or block is valid. Consensus mechanisms coordinate which valid history to follow when proposals conflict. Finality describes the conditions under which reverting an accepted history becomes unlikely, costly or forbidden under assumptions. A majority cannot simply make invalid coin creation valid to nodes enforcing unchanged rules.

Temporary forks arise when participants see different proposals or network conditions. Reorganizations can remove previously observed inclusion. Applications should distinguish pending, included, confirmed and finalized states instead of treating the first receipt as permanent settlement.

03 / FIELD NOTES

Consensus security is not application security

An honest network can faithfully execute a vulnerable contract.

Ordering attacks may censor or reorder transactions without forging another user’s signature. Network partitions can threaten liveness; validator concentration can affect censorship resistance. The scope of an attacker depends on the protocol and resources, not just a generic “51%” label.

Even perfectly agreed execution can transfer assets to the wrong recipient if contract logic, signatures or front-end instructions are wrong. Analyze consensus, contract authorization and user interaction separately. Immutable execution amplifies the importance of checking what was actually authorized.
