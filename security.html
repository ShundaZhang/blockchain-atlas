01 / FIELD NOTES

Inspect both code and privileged powers

Many failures come from valid execution of an unintended action.

RiskMechanismUseful check
Access controlUnauthorized caller changes sensitive statePositive and negative tests for each privileged function
ReentrancyExternal call returns before critical state is settledAnalyze call graph, state ordering and a suitable guard
Oracle manipulationA manipulable or stale value drives an economic decisionSource, freshness, bounds and failure handling
Approval abuseA spender can move previously authorized tokensExact spender identity, limited permissions and revocation
Upgrade controlAn administrator replaces executable logicProxy/admin graph, delay and governance controls

02 / FIELD NOTES

Transaction ordering is part of the threat model

A valid transaction may execute in a different context than expected.

Public pending transactions can reveal a trade before execution. Ordering participants can place other transactions around it, affecting pool state or inclusion. MEV includes several strategies and roles; it is not just one contract bug. Use explicit output bounds and deadlines where the application needs them.

Signatures, permits and account recovery also need domain separation, nonces and expiry semantics. Replay-safe encoding does not make a malicious approval benign. Front ends and RPC responses are part of the user’s decision path, even if contract execution is deterministic.

03 / FIELD NOTES

Use several forms of verification

Compilation, testing, source verification and audit answer different questions.

Compilation checks language and code generation; tests exercise selected behaviors; fuzzing explores inputs and invariants; source verification connects published code/settings to deployed bytecode; review or audit examines broader logic and assumptions. None alone guarantees all economic and operational behavior.

For StudyToken, check supply conservation and both successful and rejected transfers; for MessageBoard, check owner authority and the unchanged state after rejection. For a real financial protocol, extend the scope to oracle behavior, adversarial composition, governance and incident operations.
